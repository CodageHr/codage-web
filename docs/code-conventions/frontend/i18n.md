# i18n

Localization uses **i18next** + **react-i18next**. Locale files are bundled in
`src/locales/langs/` (`hr.json`, `en.json`). Default language is **`hr`**, fallback `hr`.

The active language lives in the **URL**: every route is under `app/[lang]/`, so
`/hr/…` and `/en/…` are separate statically-generated pages. This is what makes the
English version crawlable — a client-side toggle would be invisible to search engines.

## Using translations

```tsx
'use client';
import { useTranslate } from '@base/locales';

function Cta() {
    const { translate } = useTranslate(); // `translate` is an alias of i18next `t`
    return <Button>{translate('contactUsLabel')}</Button>;
}
```

- `useTranslate()` → `{ t, translate, i18n, ready }`.
- `useLocales()` → `{ allLangs, currentLang }` (used by the theme for MUI locale +
  date-fns adapter).
- `useCurrentLang()` → the active `Lang` (`'hr' | 'en'`) from the route.
- **Switching language is a navigation**, not a function call: `<LocaleSwitch>`
  links to the same page in the other locale. There is no `onChangeLang`.

## Server vs client

- **Client text** → i18next via `useTranslate()`. `getI18nInstance(lang)` builds one
  instance per locale (`src/locales/i18n-instance.ts`); `I18nProvider` (in the
  `[lang]` layout) supplies it through `<I18nextProvider>`. The i18next package
  singleton is never used — it would leak the language across routes during a
  two-locale build.
- **Page metadata** (`generateMetadata`) runs on the server and must NOT touch
  i18next. Copy lives in `src/locales/seo/` (typed) and is assembled by
  `buildMetadata(lang, routeKey)` in `src/lib/seo/`.

## Server-safe locale constants

`Lang`, `LANGS`, `DEFAULT_LANG`, `isLang`, `toLang` live in **`src/locales/langs.ts`**,
which is deliberately NOT `'use client'`. `config-lang.ts` (MUI/date-fns bundles) is a
client module — importing a *value* from it into server code (e.g.
`generateStaticParams`) yields a client-reference proxy, not the real array
(`LANGS.map is not a function`). Server code imports from `langs.ts`.

## Internal links

Use `paths.*` (locale-free) with `RouterLink`. `RouterLink` prefixes the active
locale and normalises the trailing slash via `localizeHref()`, so call sites never
hard-code `/hr` or `/en`. External links (`mailto:`/`tel:`/`http`), protocol-relative
URLs, and pure `#anchors` pass through untouched. Section anchors are English
(`#services`/`#process`/`#contact`) and shared across locales.

## Rules

- **Never hardcode user-facing strings** — always use a key.
- Add every new key to **both** `hr.json` and `en.json`, in the same order. Parity
  is checked easily: both files must have the identical key set.
- Keys are flat (e.g. `home_hero_caption`, `contactUsLabel`).
- New SEO copy → add to `src/locales/seo/` for BOTH locales (it is typed
  `Record<Lang, …>`, so a missing entry is a compile error).

## SSR safety (do not regress)

The i18n instance must render the **same** text on the server and the client, or
React 19 throws a hydration error. What guarantees it now:

1. `getI18nInstance(lang)` initialises **synchronously** (`initImmediate: false`)
   with inline resources, so `t()` resolves on the first render (server + client).
2. The language comes from the **route param**, passed down by the `[lang]` layout
   to `I18nProvider` — server and client agree by construction. There is **no
   `localStorage` read during render** (the old mechanism); do not reintroduce one.

When adding text near the top of the tree, verify the browser console shows **no
hydration warnings** on both `/hr/…` and `/en/…`.
