# i18n

Localization uses **i18next** + **react-i18next**. Locale files are bundled in
`src/locales/langs/` (`hr.json`, `en.json`). Default language is **`hr`**, fallback `en`.

## Using translations

```tsx
'use client';
import { useTranslate } from '@base/locales';

function Cta() {
    const { translate } = useTranslate(); // `translate` is an alias of i18next `t`
    return <Button>{translate('contactUsLabel')}</Button>;
}
```

- `useTranslate()` → `{ t, translate, i18n, ready, onChangeLang }`.
- `useLocales()` → `{ allLangs, currentLang }` (used by the theme for MUI locale +
  date-fns adapter, and by the language switcher).
- Switch language with `onChangeLang('en')`.

## Rules

- **Never hardcode user-facing strings** — always use a key.
- Add every new key to **both** `hr.json` and `en.json`. Keep them in sync.
- Keys are flat (e.g. `home_hero_caption`, `contactUsLabel`).

## SSR safety (do not regress)

The i18n instance must render the **same** text on the server and the client, or
React 19 throws a hydration error. Two things guarantee this — keep them:

1. `src/locales/i18n.ts` initialises **synchronously** (`initImmediate: false`) so
   `t()` resolves on the first render, and is imported for its side effect from
   `src/locales/use-locales.ts` (a `'use client'` module) so it runs on the client.
2. `src/utils/storage-available.ts` → `localStorageGetItem` returns its
   `defaultValue` when `localStorage` is unavailable (server), so the server picks
   the same default language (`hr`) as the client's first render.

When adding text near the top of the tree, verify the browser console shows **no
hydration warnings**.
